## No build, no server

`dist/` is the whole site: `index.html`, `styles.css`, and plain scripts loaded in order. There's no framework,
bundler or package to install. Every script attaches to one global, `window.SSS`:

```
core.js               pure logic: scoring, shuffling, sampling, deadlines, card review, progress validation
progress-validation.js  the nested checks behind import validation
data/*.js             SSS.SRC, SSS.MODULES, SSS.QUESTIONS, SSS.SCENARIOS, SSS.CARDS, plans
store.js              progress in localStorage, stale-tab protection, visible fallback
ui.js                 rendering helpers, question rendering, plan progress, readiness evidence
views-*.js            pages, registered on SSS.views
app.js                hash router (#/course, #/module/m05, #/practice/session …), navigation, banners
```

It works opened straight from disk (`file://`) or from any static host. `.openai/hosting.json` points the existing
hosting at `dist/`. The page sets `noindex, nofollow`, makes no network requests of its own, and keeps everything in
the browser.

The data files use the same IIFE pattern as the logic (`(function (root) { … })(window || globalThis)`), so the Node
scripts in `scripts/` can load them without a browser. See `scripts/load.js`.

## Content as data

| Item | Count | Shape |
| --- | --- | --- |
| Modules | 16: 8 shared, 4 PSM, 4 PSPO | `m01`–`m16`: objective, explanation, worked example (the fictional "Launchpad" onboarding portal), misconception, decision or sort activity, teach-back with rubric, five-question check, sources |
| Questions | 160: 80 shared, 40 PSM, 40 PSPO | `qMM-NN`: single answer, multiple answer or true/false; options, answer indexes, explanation, what the distractors overlook, `source` with a named section, a `rule` or `judgment` label, difficulty, version `v` |
| Scenarios | 8, with 17 decisions | `s1`–`s8`: a situation and 2–3 decisions, each option with its consequence, plus separate *rule* and *judgment* notes |
| Flashcards | 48 | `f01`–`f48`, tied to modules, with a reading link |
| Plans | 12 study days | days, tasks and estimated minutes |

Each question belongs to a track (`shared`, `psm`, `pspo`) and a module. A track's eligible pool is shared plus its
own: 120 questions each.

Feedback always separates three things: what the Scrum Guide requires (**rule**), concepts defined in other sources
such as the EBM Guide, and situational advice (**judgment**). The course is written to be honest about that
difference.

## Sources and the audit trail

`data/sources.js` holds `SSS.SRC`, the named external sources, and `SSS.sg(anchor, section)`, which builds a link to
one section of the Scrum Guide. Every question cites a precise section. A collection page such as "Resources for
Product Owners" is not accepted as a question's authority.

Three files keep content and sources honest:

- **`source-audit.json`:** one dated review per learning item (232 in all: modules, questions, scenarios and
  cards). Each record stores a **SHA-256 digest of the item as reviewed**. If an item changes afterwards its digest
  no longer matches, and the checks report a stale review. Editing content can't silently inherit an old review.
- **`competency-map.json`:** maps every published PSM I and PSPO I focus area (25 rows) to the lessons, scenarios
  and questions that practise it. Each area needs at least one direct question from an eligible track.
- **`content-register.md`:** generated by `npm run register` from the two files above. It lists every source section
  and the lessons, questions, scenarios and cards that use it. It refuses to build if any review is stale.

`scripts/audit-contract.js` holds the shared rules: digests, the inventory of items, and the focus-area lists.

## Progress and storage

All progress is one JSON object in `localStorage` under `scrum-study-studio:v1`. `core.emptyState()` defines its shape:
settings, module progress, attempts, scenarios, rehearsals, cards, mistakes, flags, notes, self-reported results,
checklists and a `revision` counter.

- **Visible fallback.** If storage is blocked or full, the course keeps working in memory and a banner says progress
  isn't being saved and suggests exporting. It never claims a save that failed.
- **Unreadable data is kept.** If saved progress doesn't validate, it's copied to
  `scrum-study-studio:v1:unreadable-<time>` before starting fresh, and the banner says so.
- **Stale-tab protection.** Each tab remembers the exact text it last saved. Before every write, and on the browser's
  `storage` event, it checks that storage still holds that text. If another tab has saved since, this tab becomes
  **read-only**: it shows a reload button and still allows export, so it can never overwrite newer work.
- **Export and import.** Progress exports as JSON. Imports go through strict validation (`core.validateProgress`
  and `progress-validation.js`): every id must exist in the current content, and nested records such as flashcard
  history, active rehearsals, selections, notes and results must be well-formed. Validation never mutates the input,
  and nothing is replaced unless it passes.
- **Migration.** Older progress is upgraded on load, for example the retired four-day schedule becomes the 12-day one.
  Compatible older exports import cleanly.
- **Reset** asks for confirmation.

## Practice

- **Scoring** is an exact match on the set of selected options, with no partial credit. An empty answer is wrong.
- **Shuffling:** options are shown in a shuffled order, stored per question as original indexes, so answers are
  recorded against the original options. True/false keeps "True" first.
- **Quick set:** ten questions from a chosen pool, unseen ones first. **Topic set:** all ten questions for one
  module. **Missed and uncertain:** up to 20 from the mistake notebook.
- Each answer can be marked **"I'm not sure"**, which keeps it in review even when it's right.
- After each answer, feedback shows the explanation, what the other options overlook, the rule or judgment label,
  the source section, and a link back to the module.
- Any question can be **flagged** as unclear, with a note, for the author to review.

## Timed rehearsals

A rehearsal is 80 questions in 60 minutes from one track's 120 eligible questions.

- **Sampling** (`core.sampleRehearsal`) spreads questions evenly across the track's modules, preferring unseen
  questions in each, fills any shortfall from the rest of the pool, then shuffles.
- **Fixed deadline.** The rehearsal stores an absolute deadline, start time plus 60 minutes, not a countdown. The clock
  keeps running if the tab is hidden, the page is closed or the device sleeps. Answers are saved as you go, so they
  survive a refresh. A watchdog in `app.js` submits an expired rehearsal automatically with the saved answers.
- **Grading** records the content version. A rehearsal taken on an older version of any question counts as
  **historical**, not current evidence. Each question's `v` is bumped when it changes materially.

## Flashcards and the mistake notebook

- **Flashcards** use a small Leitner-style scheme (`core.reviewCard`):
  - *missed:* back to the start, due again in 10 minutes;
  - *partial:* due in a day;
  - *recalled:* move up a box, due in 1, then 3, then 7 days.

  Each card keeps its last 20 reviews and the gap in days before each one. That gap is what "delayed recall" in
  Readiness measures.
- **Mistake notebook:** wrong answers and answers marked "not sure" go here. A confident correct answer resolves an
  item.

## The study plan

The recommended plan has 12 study days with an editable start date and flexible pacing. Tasks can link straight into
the course: a lesson, a scenario, a practice set or a manual task such as taking an official Open assessment. Unfinished
work carries forward, and estimates come from the activities themselves. Home always shows the **next useful step**.

## Readiness

Readiness shows evidence for each track separately and never predicts a pass. `ui.readiness(track)` checks eight
things:

| Check | Met when |
| --- | --- |
| Lessons | every module for the track is complete (decision activity, teach-back, lesson check) |
| Scenarios | every scenario for the track is worked through |
| Teach-backs | at least 75% rated "I could explain this clearly" |
| Rehearsals | two current-version rehearsals at **90%+** on different days |
| Mistakes | at most 3 unresolved incorrect answers, and no module with 2 or more unresolved |
| Delayed recall | at least 10 reviews a day or more apart, with 80% recalled |
| Official Opens | self-reported 100% on Scrum Open on two dates (PSPO: Product Owner Open too) |
| Rules | the exam requirements and conduct rules marked as reviewed |

The status reads *Foundation in progress* until the shared modules are done. It reads *Repair these topics* if
mistakes recur or the last rehearsal was under 85%. Otherwise it's *Suggested preparation checks complete* or *Review
your evidence before sitting*.

## Updating content safely

1. Edit `dist/js/data/`. If a question changes materially, bump its `v`.
2. Review the changed items against their sources and update their `source-audit.json` records (status, date,
   evidence, digest). Update `competency-map.json` if a question's topic changes.
3. Bump `SSS.CONTENT_VERSION` in `sources.js` and the `?v=` query strings in `index.html`.
4. Run `npm run validate`, `npm test` and `npm run register`, and note the change in `CHANGELOG.md`.

Keep precise section citations, and keep Scrum Guide rules apart from other concepts and judgment. Write
explanations in the course's own words.

## Checks

- `npm run validate` (`scripts/validate-content.js`) checks:
  - counts, ids and answer keys;
  - every source URL, and every Scrum Guide anchor against the list of real anchors;
  - plans and the audit contract;
  - **risky wording**, such as promises of passing.

  `--links` also requests each external URL. scrum.org refuses automated requests, so check those pages in a browser.
- `npm test` (`node --test scripts/*.test.js`, 24 tests) covers:
  - scoring, option shuffling and rehearsal sampling;
  - the absolute deadline and review scheduling;
  - persistence, storage failure, strict imports and stale-tab protection;
  - migration, start-date changes and readiness;
  - the audit contract and earlier corrections.
- `npm run register` regenerates `content-register.md`.
- `node scripts/screenshots.js` regenerates the README images in `docs/screenshots/`. It opens the course with a fresh
  profile and seeded randomness, so the same question appears each time. It needs Playwright with Chromium.
